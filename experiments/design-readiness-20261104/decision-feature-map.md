## What should inform the discussion first

The current measured bottleneck is inside generation:93.91% of the selected-versus-DFlash full-request wall gap on the **same natural24 cohort** falls inside the server generation interval. That interval combines drafter, target verification, target-feature catch-up/cache and scheduling. Current selected acceptance is32.02%, paired DFlash76.59%; component attribution is still needed before selecting a kernel or head remedy. Payload size alone does not establish critical-path latency.

Prioritize native state/capture/round accounting and a small set of compatible loss/data experiments. Sign scope, scale granularity and correction/head cost deserve decision-ready preparation because they change what long QAT would train and what deployment must execute. Historical short negatives remain scoped evidence; no family is universally eliminated. Most canonical segments were short (80/98 below300TRAIN seconds), so old screening dispositions cannot support a universal early rejection rule.

## Row scales versus hypothetical within-row groups

`RowBinaryLinear` requires `scale_layout="row"`; scales have shape`[M]` for weight matrix`[M,K]`. `modern_actor.enable_scale_only` freezes every parameter and enables exactly nine`scale_offset`vectors; it also verifies frozen signs. Native metadata requires`scale_group_size=0`, and the loader enforces one F32 value per output row. These are independent source facts, not shorthand for nine scalars. See `src/w1a1_eagle/recurrent_qat.py:236`, `scripts/w1a8_generalization/modern_actor.py:195`, and frozen native `src/models/eagle3.cpp:73`.

The table is **dimensional arithmetic only**, holding the existing nine projection shapes/signs and per-token A8 rule fixed. G128 is a historical reference point for costing, **not a selected design or a representation experiment**.

G128 would have1,819,200 scale values, **23.663×** the current76,880. The F32 scale payload rises307,520→7,276,800bytes (+6,969,280bytes, about6.65MiB). Packed sign bits stay29,107,200bytes if grouping changes scales alone. Sign+scale payload rises29,414,720→36,384,000bytes; effective bits/weight for just those payloads change1.010565→1.25. These are not total GGUF sizes: other tensors, metadata/alignment and staging are excluded. Head groups account for54.97% of hypothetical grouped scales.

The computation changes as well. Present native CUDA first computes one full integer dot`d[o]=Σ_j sign(w[o,j])*q[j]`, then applies one row scale and token activation scale with declared F32 rounding. Independent groups instead need`Σ_g scale[o,g]*(Σ_{j∈g} sign(w[o,j])*q[j])`, followed by the token activation scale. A single factor after the full dot cannot express this. Current K2560/5120/7680 shapes entail20/40/60 scaled partial sums per row atG128. For one input vector independently through each of the nine projections, this is1,819,200 scaled partial sums, compared with76,880 row sums; group combination introduces1,742,320 additions in a straightforward formulation. Integer sign×A8 product count need not increase. Native fusion could avoid materializing temporary partial sums; registers, reductions, scale loads, cache traffic and synchronization still need measurement. **23.663× scales is not23.663× runtime.** This sum is an analytic operator unit, not one emitted token or server round: the feature encoder, catch-up decoder and sampled head execute with different call/row counts.

For trainable F32 scales alone, parameter+gradient+two Adam moments rise1,230,080→29,107,200bytes; parameter+moments checkpoint payload rises922,560→21,830,400bytes. Frozen initial scales, state metadata, allocator/serialization duplicates and activations are extra. If all signs also train, the232,857,600F32 sign latents+gradients+Adam already total3,725,721,600bytes before a possible931,430,400byte materialized hard-sign tensor; this all-sign footprint is **projected, not a measured fit**. Group-scale training cost cannot be derived from those bytes alone.

The implementation path after a user choice is concrete: define grouped-A8 arithmetic/order/layout; add per-group actor initialization/forward/backward; version named optimizer/checkpoint state and exact resume; version GGUF metadata/tensor shapes and Q/K scale permutation; add strict CPU/CUDA partial-sum kernels; qualify real native trajectories, verifier/replay and actual packing-inclusive/request costs. Equal group values can provide a controlled migration fixture, but floating summation order still needs an explicit numeric gate. Existing row-scale byte-patching export does not automatically become grouped export. Old R512 rotation must not be silently combined with grouping.

For comparison of implementation burden only, rank8 F16 factors on every one of the current nine matrices would add1,885,440factor bytes and942,720factor MACs for one input vector independently through each matrix, before launch/add/cache costs (`2*r*(M+K)`bytes,`r*(M+K)`MACs per matrix). That is no argument to install factors everywhere, and no latency prediction. Group scales, factor corrections and more planes trade different runtime/state costs and are joint design choices.

## Four targeted primary research checks

- **EAGLE-3** motivates recurrent training-time feedback, correct attention masks and low/mid/high feature fusion while removing a target-feature prediction constraint. This supports auditing current recurrence and cautions against universal hidden-MSE auxiliaries. It does not validate binary/grouped precision or an early predictor here. [Paper, sections3.1–3.2](https://arxiv.org/html/2503.01840v3).
- **DFlash** uses parallel block drafting with target-feature KV injection and studies position-dependent loss decay versus uniform weighting. That makes early-position weighting a relevant hypothesis; its exact schedule and architecture do not transfer automatically to this recurrent drafter. Its offline feature caching does not qualify our caches. [Paper, sections4.1–4.2/A.1/A.5.1](https://arxiv.org/html/2602.06036v2).
- **BitNet b1.58 2B4T** trains from scratch with **ternary** weights, per-token absmax8-bit activations and other architectural choices. It supports taking master-weight/resource and native-kernel requirements seriously; it does not demonstrate binary conversion, full-sign QAT or scale granularity for this drafter. [Technical report, sections2–3](https://arxiv.org/html/2504.12285v2).
- **GPTQ** shows that independent consecutive weight groups can reduce quantization error while adding metadata. Its own scale/zero-point costs and model results differ from our binary/F32-scale arithmetic, and activation quantization is outside its scope. It supplies motivation, not current acceptance or kernel-speed evidence. [Paper, section5 “Additional Tricks” and section6](https://arxiv.org/html/2210.17323v2).

No external speedup is used as a local comparator or predicted gain. The local frozen DFlash baseline remains the relevant reference. Four papers close these niche questions; this is not a literature survey.
